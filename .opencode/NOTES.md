## Все операции с прошивкой — только через docker
Образ `tempotec-fw-tools` (ubuntu + 7z, ubi_reader, mtd-utils, genisoimage,
radare2, capstone, pyelftools). Запуск: `./docker/fw.sh <команда>`
(каталог проекта → `/work`, контейнер от root: нужны симлинки/device-ноды
ubireader и uid/gid в mkfs.ubifs). Пересобрать: `docker build -t tempotec-fw-tools docker`.

Пайплайн: `./tools/make.sh {unpack|patch|build|verify|all} [имя образа]`
- `unpack` → `fw/unpacked` (ISO) + `fw/SYSTEM` (UBIFS-дерево)
- `patch [--album-level]` → `tools/patch_player.py` (патчи бинаря)
- `build [имя]` → `chown 1004:1004` → `mkfs.ubifs -x lzo -d fw/SYSTEM -e 0x1F000 -c 480 -m 0x800`
  → пересчёт md5 в `UPDATE.TXT` (`tools/fix_update_md5.py`) → `genisoimage -l` → `out/<имя>`
- `verify [имя]` → распаковать образ, сверить md5/дерево/состав патчей

Сборка прошивки: `.upt` = ISO9660; внутри SYSTEM.UBI (UBI/UBIFS), UIMAGE.BIN,
UBOOT.BIN, UPDATE.TXT, VERSION.TXT, _GITIGNO. MD5 в блоке `rootfs={...}` UPDATE.TXT
обязателен (в оригинале md5 совпадает с файлом — проверено).

## Устройство системы
- init: busybox `/etc/init.d`, systemd нет. Rootfs (`/`) смонтирован **rw** (rcS
  делает `mount -o remount,rw /`) — можно менять файлы на живом устройстве.
- `/usr/bin/hiby_player` — UI + медиатека (MIPS32 LE, stripped, 7 МБ, SQLite внутри).
  SQL-строки лежат текстом в `.rodata`.
- Медиатека: `/data/usrlocal_media.db` (ubi1_0, отдельный раздел `/data`).
- Таблица SQL-строк: база `0x9b7730`, индекс = (адрес-база)/4, 199 записей;
  прямых ссылок из кода почти нет — строки берутся по индексу (группы: alter-ы с 29,
  drop/delete с 80, insert-ы 107+ и т.д.). Поэтому «не найдено xref» ≠ «не используется».
- Диспетчер запросов медиатеки: таблица `0x9b7054` (индекс = type-5), функция `0x708d20`.
  Большие `INSERT INTO %s%d SELECT ...` (по одному на тип списка) — от `0x9bad68`.

### Алфавитный указатель
- Полоска букв — **картинка** `usr/resource/litegui/theme1/touch_list/a_z.png`
  (24×412, нарисованы `A…Z`,`#`), фон индикатора — `a_z_result_bg.png`.
- Буква в коде — однобайтовый символ: `sprintf("%c", …)`, строка `"%c"` по адресу
  `0x9EF5FC`, используется в 5 местах, в т.ч. индикатор `0x4c9ee0` и запросы
  медиатеки `0x7033f4`, `0x703404`, `0x7035a4`.
- Позиция→буква: `0x4c9278` (`letter = 'A' + index`), предел `0x4c927c` (`slti …,0x5b`),
  запасная буква `'#'` (`0x4c9140`, `0x4c9280`).
- Прыжок по букве: `fcn.00703320` — биндит два одиночных символа и выполняет
  `SELECT count(id) FROM X_TABLE WHERE character >= ? AND character < ?` (и родственные).
  **Следствие: порядок строк в таблице списка обязан совпадать с порядком по `character`**,
  иначе прыжок уезжает.
- Где полоска есть, а где нет (проверено пользователем на устройстве):
  - **All** — есть (транслит не применяется — вероятно, там другой источник букв, проверить),
  - **Albums** — есть, транслит работает; на подуровне (треки альбома) полоски нет,
  - **Artists** — есть, транслит работает; на подуровнях (альбомы артиста, треки) нет,
  - **Genres** — нет,
  - **Album Artist** — нет ни на одном уровне.
- Включение механики в обработчике списка (0x4c9078–0x4c90a4): два гейта —
  `view->0x10 == 1` (0x4c908c) сразу отключает полоску для этого вида, и затем
  `[view->0x258][0x3b6c][0x1fc] != 0` (0x4c9094–0x4c909c). Прямых записей в `+0x1fc`
  в `.text` не нашлось (0 штук) — значит поле приходит из структуры/таблицы, которую
  куда-то копируют; это следующая зацепка, если захочется включить полоску в
  Genres / Album Artist / подуровнях.
- В UI (рус. локаль) пункт USB «Стыковка», в англ. — «Dock», но в этой модели он
  из меню вырезан.

## Патчи кода (tools/patch_player.py, tools/patch_sql.py)
1. **SQL-фикс** (строка `0x9bad68`, запрос «треки альбома у артиста»):
   было `WHERE (album = ? AND artist = ? ) AND ((has_child_file = 0 …`;
   стало `WHERE (album = ?1 AND (artist LIKE ?2 OR album_artist LIKE ?2)) AND has_child_file IN (0,1,2))`.
   Длина сохранена (padding), параметров столько же (?1 альбом, ?2 артист).
   Проверка семантики — `tools/test_query.py`.
2. **Уровень альбомов** (флаг `--album-level`, 4 байта): в обёртке `0x4aa1c4` имя
   открываемого вида `lui a2,0x96` (`0x4aa208`) + `addiu a2,a2,0x948` (`0x4aa21c`)
   → смещение `-0x2d1c` (вид `0x95d2e4 vg_listview_albums_of_an_artist`).
   В одиночку этого мало: нужен ещё уровень «альбомы» из `artist`-ключа.
3. Эксперимент (не в сборке): `tools/exp_letters.py` подменяет базовую букву/предел
   индикатора (проверяли кириллицу — буква режется до 1 байта, поэтому в сборку не пошло).

Патчи-заготовки к SQL-строкам (когда понадобится): строку можно **перенести** в
свободное место `.rodata` и **переписать указатель в слоте** таблицы, либо поправить
пару `lui/addiu` в коде, если строка адресуется напрямую. Свободное «нулевое» место в
`.rodata`: `0x93f607`, ~4477 байт (использовать только первые ~1.7 КБ: с `0x93fce0`
внутри дыры есть ссылки из кода — там пустые строки).

4. **SQL-сборка списков** (`tools/patch_sql.py`):
   - слоты 124–127 (таблица SQL `0x9b7730`): буква приводится к `A–Z`
     (`CASE WHEN character BETWEEN 'A' AND 'Z' THEN character ELSE '~' END`), сортировка
     `ORDER BY 3, <имя>`; слот 125 («Артисты») дополнительно берёт данные из
     `ALBUM_ARTIST2_TABLE` (перенесена в `0x93f610`), остальные — по месту;
   - точечные правки сортировок внутри строк (26 мест, длина сохраняется):
     `ORDER BY name/path … COLLATE pinyin` → `ORDER BY character, …` — иначе прыжок
     по полоске не совпадает с порядком строк (в «All» русские треки лежали в конце).
   Зачем: полоска считает позицию как «число записей с `character` меньше буквы», поэтому
   таблицы списков обязаны быть отсортированы по `character`; а «Артисты» должны браться
   из авторов альбомов. Проверено на устройстве: после «обновления медиатеки» плеер сам
   собирает ARTIST_TABLE (51 запись), ALBUM_TABLE, ALBUM_ARTIST_TABLE, GENRE_TABLE
   отсортированными по букве, без единого лишнего процесса.

## Работа с устройством (adb)
- Включается скриптом `/etc/init.d/S98adb_debug` — он есть только в отладочном образе
  `out/v3_analog_artists_with_adb.upt` (в релизном его нет). Скрипт всегда активен
  (файл-маркер больше не нужен): `enable=0 → idVendor=18d1 → idProduct=0d02 →
  functions=mass_storage,adb → enable=1`, затем `/sbin/adbd`; лог — `/mnt/sd_0/adb_boot.log`
  (и `adbd.log`). Причина, почему первая версия не работала: писать `functions` можно
  только при `enable=0`.
- Канал капризный: живёт в первые ~3 минуты после включения, иногда хост не видит
  устройство — помогает `adb kill-server` и/или перезагрузка плеера.
- `adb` на ПК: `/usr/bin/adb` (android-tools), устройство видно как `TempoTec V3`.
- Убить `hiby_player` (`killall hiby_player`) = устройство уходит в перезагрузку.
  Порядок итерации: `adb push <bin> /usr/bin/hiby_player` → `sync` → `reboot` → ждать ~45 с.
- БД: `adb pull /data/usrlocal_media.db work/device/…`, правится локально, затем
  `adb push` + `sync` + `reboot` (правки переживают перезагрузку).

### Что уже сделано с БД (для указателя)
Хронология (скрипты в `tools/`, работают по локальному файлу БД):
1. `translit_db.py` — буквы в колонке `character`. Две разные логики:
   у сущностей (ARTIST/ALBUM/ALBUM_ARTIST/GENRE/FORMAT/BOOK) кириллица переводится в
   латиницу (А→A, Б→B, В→V, …, Кино→K, Дайте танк→D); у **треков**
   (`MEDIA_TABLE`/`MEDIA3_TABLE`) буква считается по **названию** трека (плеер сам ставит
   её по исполнителю — из-за этого поиск в «All» не совпадал с порядком). Всё остальное
   (цифры, символы) → `~` в конец списка. Плюс триггеры `fix_char_*` (вставка) и
   `fix_char_upd_*` (обновление имени) на `*2_TABLE`, `MEDIA_TABLE`, `MEDIA3_TABLE`.
2. `reorder_db.py` — таблицы списков пересобраны `ORDER BY character, имя`
   (включая `MEDIA_TABLE`/`MEDIA3_TABLE`, из которых читается «All»).
3. `album_artist_db.py` — `ARTIST_TABLE`/`ARTIST2_TABLE` наполнены **авторами альбомов**
   из `ALBUM_ARTIST2_TABLE` (51 запись вместо 75 трековых артистов) и пересортированы.
   Смысл: категория «Артисты» умеет полоску, а «исполнитель альбома» — нет; так
   получается «автор альбома → альбомы → треки» с работающим алфавитом.

Состояние на устройстве: бинарь = все патчи (см. выше), БД = транслит + буквы треков по
названию + сортировка по `character` + «Артисты» из авторов альбомов. Всё подтверждено
пользователем: Artists / Albums / Album artists / Genres / All ищутся корректно.

## Список «All» (все треки) — разобран

Разбор закончен, список работает.

Что выяснилось: у треков в таблицах сканирования (`MEDIA2_TABLE`) колонка `character` —
это первая буква **исполнителя** (`Rebirth` у DECO*27 → `D`), а сам список «All» читается
из `MEDIA_TABLE` и идёт по **названию трека**. То есть буква и порядок были из разных
миров — полоска не могла совпасть.

Решение:
1. в базе на `MEDIA_TABLE`/`MEDIA3_TABLE` стоят триггеры (`fix_char_*`), которые считают
   букву трека **по названию** (`A–Z`, всё остальное → `~` в конец) — при вставке и при
   обновлении названия; так же проставлены буквы существующим записям
   (`tools/translit_db.py`, теперь обрабатывает и эти таблицы);
2. `MEDIA_TABLE` пересортирована по `character, name` (`tools/reorder_db.py`);
3. в прошивке сборка `MEDIA_TABLE` идёт `ORDER BY character, name` (`tools/patch_sql.py`,
   текстовые правки сортировок) — так что после обновления медиатеки порядок снова
   будет правильным автоматически.

Проверено пользователем: поиск в «All» совпадает с буквами, треки на цифры/символы
уезжают вниз.

Важно для будущих правок: у треков буква — по названию (как мы и сделали), у сущностей
(исполнители, альбомы, авторы альбомов, жанры) — транслит кириллицы в латиницу. Это две
разные логики, и `tools/translit_db.py` держит их раздельно.

## Сдвиг буквы при прыжке по полоске — **исправлено**

Причина: плеер считает позицию для прыжка как «число записей в диапазоне
`character >= 'A' AND character < буква`» и берёт строку с этим номером. Значит записи,
чьи буквы меньше `A` (альбомы/треки, начинающиеся с цифры или символа: `"LED Spirals"`,
`$WING`, `[Oops]`, `500 K`, `14:0`), стоят в начале списка, но в счёт не попадают — и
сдвигают все прыжки вниз на свою длину. Проверка на реальной БД: `ARTIST_TABLE` (без
таких записей) — 0 ошибок; `ALBUM_TABLE` (15 таких записей) — «A» попадал в `"`, «C» в
`A`, «H» в `F` и т.д.

Решение (в прошивке, `tools/patch_sql.py`): при сборке списков буква приводится к
`A–Z`, а всё остальное заменяется маркером `~` и уезжает в конец списка. Важно: маркер
обязан быть *больше* `z`, потому что сортировка идёт с `COLLATE NOCASE` (буквы приводятся
к нижнему регистру, и `[` = 0x5B оказывается меньше `z` = 0x7A — первая попытка с `[`
не сработала). Плюс поправлены сортировки в запросах списков треков
(`ORDER BY name/path … COLLATE pinyin` → `ORDER BY character, …`, 26 мест).

Проверено пользователем на устройстве: Artists, Albums, Album artists, Genres и «All» —
прыжки совпадают с буквами, записи на цифры/символы лежат внизу.

Инструменты эксперимента (`tools/exp_jump_shift.py`, `tools/exp_letters.py`) в релиз не
входят, оставлены как справка.

## Списки: таблица видов и классы

- Таблица видов `0x95e770`, 109 записей × 0x3c байт (15 слов). Поля:
  [0]=имя (UPPERCASE, напр. `VG_LISTVIEW_ALBUM`), [1]=type (идёт в `view+0x40`),
  [2]=селектор шаблона строки (0=`@class@`, 1=`@music@`), [3], [4..0xc]=флаги
  (биты `view+0x74`: w4=bit0, w5=bit1, w6=bit2, w7=bit5, w8=bit6, w9=bit7,
  w10=bit8, w11=bit9, w12=bit10), [0xd]→`view+0x41e0`, [0xe]=строка-ключ
  (идет в `view+0x3828`; у «Альбомы»=`"album"`, «Артисты»=`"artist"`,
  у «альбомы артиста» — пусто).
- Флаг **bit0 (`w4`)** включает фоновый загрузчик обложек (`FUN_004cbba0` +
  поток `FUN_004cb810`, парсер `FUN_004ca500`). Среди альбомных видов bit0 стоит
  ТОЛЬКО у `VG_LISTVIEW_ALBUM` (idx 3 в таблице видов; idx 6 в массиве путей),
  ещё у EXPLORER и DOWNLOAD_ITEM. У `VG_LISTVIEW_ALBUMS_OF_AN_ARTIST` (idx 21 /
  путь idx 88) и `VG_LISTVIEW_ALBUMS_OF_A_GENRE` (idx 16 / путь 85) bit0=0.
- Параллельные массивы (в `.data`): пути шаблонов `0xabd3c8` (stride 0x20c) и
  коллбэки класса `0xabd4cc` (stride 0x20c): +0x104→`view+0x423c` (источник данных),
  +0x108→`view+0x4248`, +0x16c→`view+0x4240`, +0x170→`view+0x4244`,
  +0x174→`view+0x424c`. У всех «музыкальных» видов совпадают, кроме источника
  данных (+0x104).
- Загрузка шаблона (`FUN_004ac980` + `FUN_00497200`): путь вида
  `vg_listview_@class@<suffix>.listview` парсится `sscanf("%[^@]@%[^@]@%[^.]%s")` и
  превращается в `vg_listview_class.listview` (общий шаблон строки!). Т.е.
  «Альбомы» и «альбомы артиста» рисуются ОДНИМ шаблоном `vg_listview_class.listview`
  (там есть `listview_class_iv_cover`). Разница только в данных/коллбэках.
- Источник данных «Альбомы»: `FUN_004a95e0` → `FUN_004a1ba0(..., L"album")` →
  `FUN_0070b020(key="album")` → `SELECT * FROM ALBUM_TABLE` (строки альбомов без
  пути). «Альбомы артиста»: `FUN_004a9180` → `FUN_0070b020(key=<артист>)` →
  подготовленный запрос `FUN_007060a0` + `list_tb_<n>`, где наполнение —
  `SELECT DISTINCT album FROM MEDIA_TABLE WHERE artist like ?` (без пути/обложки).

### РАЗБОР ЗАКОНЧЕН (проверено на устройстве): обложки выводятся подменой вида

Выше раздел «обложки… тупики» **устарел** — механизм понят весь, эксперимент
подтверждён пользователем. Ниже — верные факты.

**Как рисуется обложка строки:**
- Контрол обложки называется `listview_class_iv_cover` — из общего шаблона
  `vg_listview_class.listview`. Своего файла у вида нет: `FUN_004ac980` +
  `FUN_00497200` строят `vg_listview_@%s@%s.listview`, но `sscanf("%[^@]@%[^@]@%[^.]%s")`
  берёт из имени только `class`/`music` и расширение, а суффикс вида
  (`albums_of_an_artist`) отбрасывает → грузится `vg_listview_class.listview`.
  Значит **перенос/подмена layout = подмена одного файла `vg_listview_class.listview`**.
- Запись обложки (0x948): путь — wide на байте **`+0x524`** (`piVar4+0x149`),
  имя — `+0x114`. Парсер `FUN_004ca500` по пути открывает файл или сканирует
  его папку (`cover/front/folder`).
- Путь в запись кладёт **`FUN_004a52a0`, строка 151**:
  `FUN_00420f20(record + 0x524, view + 0x3de0, 0x104)` — **источник = буфер пути
  самого вида `view+0x3de0`**, а не SQL-колонка. Асм: `0x4a5528 addiu $a1,$s0,0x3de0`.
- Вызов `FUN_004a52a0` — из `FUN_004a13c0`, только при `view+0x74 & 1`
  (бит0 = `w4` таблицы видов). У `Albums` w4=1, у вида 21 w4=0.

**Почему у `Albums` обложки есть, у «альбомы артиста» нет:**
- `Albums`: `view+0x3de0` = путь выбранного альбома (`a:\qobuz\Grandson\…`) →
  парсер находит картинку.
- вид 21: даже при `w4=1` в `view+0x3de0` лежит служебная строка (`"artist\Anacondaz"`),
  папки нет. SQL-`path` в записях вида 21 отсутствует: источник типа 9
  (`case 9` в `FUN_00708d20`) наливает `list_tb_N` через
  `INSERT INTO %s%d VALUES (?,?,?,0,…)` — **без колонки `path`**.

**Рабочее решение (подтверждено): подмена вида.**
```
0x4a8b84: addiu $a2, $a2, -0x2d1c   ; vg_listview_albums_of_an_artist
       -> addiu $a2, $a2, -0x2d58   ; vg_listview_album (категория «Альбомы»)
```
Скрипт — `tools/exp_album_view.py`. Залить `w4=1` (байт `0x55ec6c`) + эту правку:
обложки в списке появляются.

**Побочный эффект:** вид «Albums» берёт данные из `ALBUM_TABLE`
(`SELECT * FROM ALBUM_TABLE`) — там **нет артиста** (`id,album,character,cn,ctime,
mtime,mqa,pinyin_charater`), поэтому показываются **все альбомы**, фильтр по
выбранному артисту теряется. `MEDIA_TABLE` — единственный источник с `album`+`artist`.

**Направление финального решения** (вид 88 + обложки): оставить вид 88 (правильный
фильтр `SELECT DISTINCT album FROM MEDIA_TABLE WHERE artist like ?`) и научить его
класть путь — правка `case 9` в `FUN_00708d20`, чтобы в `list_tb_N` попадал `path`
(подзапрос из `MEDIA_TABLE` по имени альбома), плюс `w4=1`. Вариант-хак:
`tools/exp_cover_artist_path.py` (0x4a5528 → `addiu $a1,$sp,0x24`, т.е. путь из
`local_ec0+4`) — сам по себе не работает, т.к. `path` в записях вида 21 пуст.

## Shuffle: разбор (2026-10-07) — причина найдена, фикс в 1 инструкцию

Задача: предсказуемый обратимый random (prev→next возвращает тот же трек).
Полный разбор — `work/shuffle_design.md`.

- Режимы — `play_settings.ini`, ключ `play_mode` (`order/random/single/loop`);
  режим в рантайме — `DAT_00b03bf4`.
- Выбор индекса по режиму — **`FUN_0042da00`**: режим `2` = random, использует
  таблицу-перестановку `DAT_00b03cbc` (пары `{индекс, флаг "сыграно"}`), курсор
  `DAT_00b03cc0`, текущий `DAT_00b03c04`, размер `DAT_00b03cc4`. Режимы `3`=loop,
  `0`=order (последовательно ±1).
- Перестановка строится **`FUN_0042d720(count,1)`** (Fisher–Yates) на libc `rand`
  (stub `0xa7dbc0`, GOT `0xa92b30`); `srand` — `FUN_004738a0`, сид = хеш
  `/proc/sys/kernel/random/uuid` → порядок случаен, отдельный сид не нужен.
  (Прежняя заметка «rand=curl» — ошибка поиска по `$gp`; настоящие стабы линковки
  в `.text`: `0xa7da60` srand, `0xa7dbc0` rand, грузят GOT абсолютно `lui t7,0xa9`.)
- Плеер: поток команд `FUN_00431ac0` (entry `0x431a20`), очередь `DAT_00b03bd0`,
  таблица обработчиков `0x93c298` (код 2 = «вперёд» `0x431eec`, код 1 = «назад»
  `0x431f58`); они зовут `FUN_004f2e20`/`FUN_004f2d60` и `FUN_0042faa0`/`FUN_0042f660`.
- **БАГ:** в random-ветке «вперёд» пропускает записи с флагом «сыграно»
  (`0x42dd8c: bne $v1,$zero,0x42dc3c`), а «назад» курсор просто уменьшает → после
  «назад» «вперёд» уходит мимо только что прослушанного.
- **ФИКС:** `0x42dd8c: ab ff 60 14` → `00 00 00 00` (nop). Тогда вперёд = курсор+1,
  назад = курсор−1 по одной перестановке → обратимо; порядок случаен, без повторов
  до конца; при полном проходе таблица пересобирается. Режимы order/loop/single и
  UI не затрагиваются.
- Скрипт: **`tools/exp_shuffle_linear.py`** (идемпотентный, `--check`). Проверено
  на устройстве — работает.
- **РЕШЕНО (проверено на устройстве):** линейный проход (`exp_shuffle_linear`) +
  guard-хук (`exp_shuffle_guard`) на `FUN_0042da00` (`0x42da2c` → RX `0xa7e370`).
  Хук: если mode==2 (random) и размер таблицы `DAT_00b03cc4 != DAT_00b03bfc`
  (список сменился, напр. граница альбома) → `DAT_00b03c04 = 0` и
  `FUN_0042d720(count,1)` (пересборка перестановки). При совпадении размера хук
  прозрачен (в т.ч. путь выбора трека) — поэтому выбор трека работает.
- **Важно:** первая версия guard сбрасывала индекс безусловно при `idx >= count` —
  это ломало **выбор трека** («playback failed. file not found»). Сброс только по
  несовпадению размера списка — безопасен. `FUN_0042da00` вызывается лишь из
  `FUN_00431700` (prev) и `FUN_00431860` (next), через них же идёт выбор — хук
  обязан быть прозрачным при том же размере.
- Релиз: бинарь md5 `0c8d1ef10c1d84219f50418df6226ad7`, образ
  `out/v3_analog_shuffle.upt` (ISO `115d304bd4a223d008ad49aba96c11f3`, UBI
  `92121788547445030a6e2097406a3159`). Цепочка: coverid-цепочка →
  `exp_shuffle_linear` → `exp_shuffle_guard` (воспроизводимость из базы `4429784b`
  проверена).

## SD-карта «отваливается» в отладочных сборках (2026-10-07) — причина найдена

Симптом: плеер видит изъятие/вставку карты, но считает, что карты нет; при этом
обложек нет (список из `/data/usrlocal_media.db` есть, а картинки — файлы на карте,
их нет). Карта при этом исправна (ручной `mount -t vfat -o ro /dev/mmcblk0p1`
работает, хост видит её как USB-диск `SONSUNG`).

Причина: отладочный скрипт `/etc/init.d/S98adb_debug` настраивает USB-гаджет
`functions="mass_storage,adb"`, и LUN mass_storage указывает на **весь диск карты**
(`/sys/class/android_usb/android0/f_mass_storage/lun/file` = `/dev/mmcblk0`).
Пока USB подключён, карта принадлежит гаджету — плеер её не монтирует. Любое
USB-шевеление (adb-команда, маунт на хосте) роняет карту у плеера; ребут возвращает.
Карта при загрузке монтируется (`FAT-fs (mmcblk0p1)` в dmesg), но затем теряется.

Фикс (adb остаётся, карта возвращается плееру): в `S98adb_debug` пробовать `"adb"`
РАНЬШЕ `"mass_storage,adb"` (в цикле `for f in ...`), либо вручную
`echo 0 > enable; echo adb > functions; echo 1 > enable` + reboot. Применено на
устройстве (теперь `for f in "adb";`, гаджет `adb`, карта в `/mnt/sd_0`); рабочая
копия — `work/device/S98adb_debug.fixed` (md5 `86de3452…`). Исходника скрипта в
дереве нет — он был только в отладочном образе; при сборке нового отладочного
образа брать фикс отсюда. Тогда хост не
видит карту как USB-диск, но adb работает и карта остаётся у плеера.
ВАЖНО: `cat /sys/.../functions` и т.п. adb-активность сама по себе роняет карту при
mass_storage — не удивляться. Обложки в Artists (865e6d3a) при смонтированной карте
рисуются, переключатель работает.

## Разбор тега `artist` по `;` — находки 2026-10-07 (важно, не повторять ошибок)

### Формула матча по составляющей — ТОЛЬКО через substr, НЕ replace(char(0))
Значения в БД хранятся с хвостовым NUL (`'Green Crow\x00'`). Выражение
`(';'||replace(artist,char(0),'')||';') LIKE '%;'||replace(?,char(0),'')||';%'`
**НЕ работает**: `replace` с образцом `char(0)` NUL не вырезает (образец обрезается
до пустой строки), а встроенный LIKE обходит СУБЪЕКТ как C-строку и обрывается на
NUL — завершающая `';'` после NUL невидима. Матчится только та составляющая, за
которой `;` стоит ДО NUL (первая часть двухсоставной склейки); последняя
составляющая и одиночный артист — нет.
Рабочая форма (снимает NUL с колонки и параметра; `length()` считает символы до NUL):
```
(';'||substr(artist,1,length(artist))||';')
    LIKE '%;'||substr(?1,1,length(?1))||';%'
```
Параметр один (`?1` переиспользован) — число биндингов у плеера не меняется.
Проверено на копии реальной БД (media_split.db): треки «Дэн Субботин» 0→13,
«Green Crow» 73→86, «Дурной Вкус» 9→9; альбомы 0→5, 10→14, 4→4.
`artist = ?` без NUL даёт 0 строк, `artist like ?` — совпадения ⇒ плеер биндит
артиста ВМЕСТЕ с NUL.

### Список треков артиста — другая ветка (0x9bb000), НЕ 0x9ba000
`songs_of_artist_all` (переключатель в Artists) собирается строкой **0x9bb000**:
`... WHERE rowid in(select rowid from MEDIA_TABLE WHERE artist = ? ) ORDER BY
character,name` (точное `=`, без has_child_file). Правка 0x9ba000
(`artist like ? AND has_child_file = 0`, kind5-main) на неё НЕ влияет — отсюда
симптом «Green Crow треки есть, Дэн Субботин пусто». Для полного фикса нужно
перевести на составляющую и 0x9bb000 (адресация строки — искать пары lui/addiu
по xref, слот-таблицы там нет).

### Почему триггеры гибнут при рескане → как сделать «плеер собирает БД сам»
Плеер при «обновлении медиатеки» делает `DROP TABLE IF EXISTS ARTIST2_TABLE`
(и ALBUM2/GENRE2/FORMAT2) — вместе с таблицей гибнут триггеры `fix_char_*`/`split_*`.
Все `CREATE TABLE` — с `IF NOT EXISTS`. Идея: заменить эти 4 `DROP TABLE IF EXISTS
<*2_TABLE>` на `DELETE FROM <*2_TABLE>` (строка короче — влезает по месту), тогда
наши триггеры выживут и плеер будет строить БД правильно сам, без постобработки.
ПЕРЕД сборкой проверить дизасмом (xrefs на 0x9c0c64/0x9c0c88/0x9c0cac/0x9c0cd0
не нашлись простым xref — строки адресуются иначе/через таблицу).
`character` треков плеер берёт из `MEDIA2_TABLE` (там = первая буква исполнителя);
`INSERT INTO MEDIA_TABLE SELECT * FROM MEDIA2_TABLE ... ORDER BY character,name`
(0x9c1700/0x9c176c/0x9c17dc/0x9c184c) — копирует как есть.
