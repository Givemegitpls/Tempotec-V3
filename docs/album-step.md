# Переход «альбом → следующий альбом того же автора»

Статус: **готово и проверено на устройстве (2026-10-10)** — и «альбом→альбом», и
«последний альбом автора → следующий автор», в Artists **и** Album Artist
(бинарь `a3a29d9c…`). История: `albumstep` (`fde1e6c2…`) — альбом→альбом;
`albumstep2` (`e4939351…`) падал на границе автора; причина и фиксы — ниже.

Дополнение (2026-10-11): «назад» на границе автора (первый альбом → предыдущий
автор, его последний альбом) — сборка `out/v3_analog_albumstep6.upt`
(бинарь `ef105b98…`), **проверено на устройстве**.

История: `albumstep2` (`e4939351…`) падал на границе автора — причина
(view-ловушка `trap(7)` из EOS-потока) и первый фикс (SQL через `FUN_0070b020`)
описаны в `.opencode/NOTES.md`; затем найдены ещё два дефекта (см. ниже).

Скрипт: `tools/exp_shuffle_hierarchy.py` (в цепочке `tools/verify_build.py`
после `exp_shuffle_guard`). Разбор стока — `work/stock_album_step_design.md`.

## Проблема

При включённой настройке «Play through albums» (`album_skip`) после завершения
альбома плеер звал `FUN_004eae80`, который брал следующий/предыдущий альбом из
**глобального** `ALBUM_TABLE` (автор не учитывался) → уводило к чужому автору.

## Причина (разбор стока)

- В стоке клик по альбому в списке артиста (`FUN_004a9360`) давал ключ
  `artist\<Артист>\<Альбом>` → вид `songs_of_an_album_and_an_artist` (kind 8);
  гейт автоперехода `FUN_0042bf40` (префикс `album`) для `artist\…` **ложный** →
  глобального перехода не было.
- Наш патч обложек (`exp_album_view`) увёл клик на `FUN_004a9680`, который всегда
  ставит префикс `album` → ключ `album\<Альбом>`, kind 6 → гейт истинный →
  переход по глобальному списку.

## Решение

Два хука (заглушки в `.text`-пещере `0x4194a0`/`0x419600`, `jal` разрешён):

1. **Контекст автора** — при открытии списка альбомов автора (`FUN_004a9180`,
   хук `0x4a9288`; `s6` = ключ вида) в `.data`-дыре `0xb02bf0` пишется тип
   (`artist`=1 / `album_artist`=2) и ключ вида (`artist\X` / `album_artist\X`).
   Любой другой ключ (верхние «Альбомы») → тип 0.
2. **Подмена альбома на переходе** — хук `FUN_004eae80` (`0x4eaf2c`, вместо
   `jal FUN_004369a0`): если контекст задан и ключ плейлиста `album\<Альбом>` —
   перебираем **штатной** `FUN_004369a0(ключ_автора, i, scratch)` (i=0..63) список
   альбомов автора, ищем запись с `scratch+0x42c` == `rec+0x20c` (текущий альбом).
   «Вперёд»: берём i+1; если запись пуста или её имя совпало с текущим — идём в
   п. 3 (следующий автор), иначе копируем имя в `rec+0x20c`. «Назад»: i−1
   (i==0 → fallback). Иначе/ошибка — штатный `FUN_004369a0` (fallback).
3. **Следующий автор** (forward-граница). Тип ctx → ключ списка сущностей
   `L"artist"`/`L"album_artist"`; имя текущего автора лежит в ctx по `+0x12`
   (`artist\`) / `+0x1c` (`album_artist\`). Перебираем список сущностей и ищем
   текущего автора по `scratch+0x20c`; берём j+1 (пусто/совпало → fallback).
   Собираем ключ `artist\<новый автор>` в буфере, **строим список альбомов нового
   автора** (`memset(rec); rec+0x004=полный ключ; rec+0x52c=имя без префикса;
   FUN_0070a3a0(9,0,rec,0)`) — иначе его не найти; затем берём первый альбом;
   пишем его в `rec+0x20c` и обновляем ctx-ключ. Дальше `FUN_004eae80` собирает
   kind-6 список и стартует сам.

**Почему чтение строк идёт через `FUN_0070b020` (SQL), а не `FUN_004369a0`:**
из потока завершения трека (NON-main-thread) путь «живого вида»
(`FUN_004424a0`→`FUN_004ec900`→`FUN_004a4b40`) для ключа-сущности делает
`trap(7)` → ребут (так падал `albumstep2`). `FUN_0070b020` — тот же SQL-fallback,
что и внутри `FUN_004369a0` (`0x436a3c`), вид не трогает. Список альбомов автора
(`list_tb`) строится только `FUN_0070a3a0(9,…)` — `FUN_004369a0` его не создаёт.
`FUN_0070a3a0` из этого потока безопасна — сток сам зовёт её там же
(`FUN_004eae80`, kind 6).

## Грабли

- Wide-слово префикса собирается как `второй_символ<<16 | первый_символ`:
  `artist` = `0x0072_0061` (не `0x0061_0072`), `album_artist` = `al` (`0x006c_0061`).
  Ошибка здесь → тип 0 → fallback (так и было сначала: Artists не работал,
  Album Artist работал, т.к. проверка `al` была верной).
- В kind-9-записи имя альбома лежит и в `rec+0x20c`, и в `rec+0x42c`.

## Проверка на устройстве (пройдена)

Artists → `Дэн Субботин` → альбом → доиграл → следующий альбом `Дэна`;
Album Artist → `Дэн Субботин` → аналогично; «назад» с первого трека → предыдущий
альбом.

**Чек-лист для «следующего автора» (albumstep4):** Artists→автор→доиграл все его
альбомы → должен включиться первый альбом **следующего автора** (не повтор и не
чужой по глобальному списку); Album Artist — аналогично; «назад» на первом
альбоме автора → штатный fallback; Artists/Albums/All/Files не задеты. Если снова
падение на границе автора — собрать `--diag` (маркеры в `/mnt/sd_0/hier2.log`).
Откат — `adb push` known-good бинаря + `reboot`.

## Известное поведение / что осталось (на момент передачи)

**Проверенная на устройстве сборка (альбом→альбом):** бинарь
`fde1e6c26e08a7909ceeb4b4e1b93ce9` (образ `out/v3_analog_albumstep.upt`).

**Следующий автор — РАБОТАЕТ (проверено на устройстве 2026-10-10).** Бинарь
`a3a29d9c…`, образ `out/v3_analog_albumstep5.upt`. История падений/фиксов:

- `albumstep2` (`e4939351…`) падала **на границе автора**: в ветке `eos_next_author`
  `F_WCPY` вызывался с перепутанными аргументами (писал в строку `L"artist"` в
  `.rodata` вместо буфера ключа). Исправлено.
- Крах **при открытии исполнителя**: диагностический `lg()` не сохранял `t2`
  (указатель на ctx) → запись по мусору. Исправлено (`lg` сохраняет `t2,t7,t8,t9,v0`).
- Граница уходила в штатный fallback (глобальный список): `rec+0x52c` клалось
  **имя без префикса**, но сборка применяет `exp_albums_artist_album_artist.py`
  (`0x4a9214: jal FUN_0049d760 → jal FUN_00420f20`), т.е. в СОБРАННОМ стоке
  `rec+0x52c` = **полный ключ** `artist\ИМЯ` (slot 182 ждёт именно его). Фикс —
  `rec+0x52c` ← полный ключ (keybuf).
- Album Artist уходил в fallback: имя автора в ctx читалось по `ctx+0x1c`, но для
  `album_artist` оно с `**ctx+0x1e**` (`album_artist\` = 13 wide = 26 байт). Фикс —
  `addiu t0,t0,0x1e` в ветке `na_aa`.

**Как читается список автора:** `FUN_004369a0(key,idx,rec)` ищет ОТКРЫТЫЙ
экземпляр вида (`FUN_004ec900`, по `view+0x3de0==key`); если нет — уходит в
`FUN_0070b020`, у которого есть финальный fallback `FUN_007060a0(key)` →
`MANAGER_TABLE` → `list_tb_N limit ? offset ?` (`FUN_00700940`). Для НЕоткрытого
автора экземпляра нет, но список, построенный `FUN_0070a3a0(9,…)`, регистрируется
в `MANAGER_TABLE` — и `FUN_0070b020` его находит. Дизайн-документ —
`work/next_artist_reader_design.md`.

- **Последний альбом автора** больше не повторяется: при совпадении целевого
  альбома с текущим (или пустой записи) хук уходит в п. 3 — следующий автор;
  если следующего автора нет или что-то не сошлось — штатный fallback
  (`FUN_004369a0(L"album", idx, rec)`).
- **Направление «назад» на границе автора** (первый альбом автора) теперь ведёт к
  **предыдущему автору** и его **последнему** альбому (симметрично «вперёд»).
  Сборка `out/v3_analog_albumstep6.upt` (бинарь `ef105b98…`), **проверено на
  устройстве**. Реализация: ветка `eos_prev_author` в
  `tools/exp_shuffle_hierarchy.py` — по списку сущностей берём `j-1`, строим
  список альбомов предыдущего автора (`FUN_0070a3a0(9,…)`) и циклом по строкам
  берём ПОСЛЕДНИЙ непустой альбом (ридер за концом списка не чистит `rec`, поэтому
  результат копируется в отдельный буфер `sp+0xc00`; кадр `eos` расширен до
  `0xe00`).
- **Адреса:** `FUN_004369a0` (`0x4369a0`), `FUN_004eae80` (`0x4eae80`),
  `FUN_004a9180` (`0x4a9180`), `FUN_0070a3a0` (`0x70a3a0`), `FUN_0070b020`
  (`0x70b020`), `FUN_007060a0` (`0x7060a0`), `memset` (`0xa7dfb0`).
- **Грабли:**
  - записи сущностей (`ARTIST_TABLE`/`ALBUM_ARTIST_TABLE`) кладут имя в
    `rec+0x20c` (маппер `FUN_007005e0`);
  - в записи под `FUN_0070a3a0(9,…)` `rec+0x004` = `rec+0x52c` = **полный ключ**
    `artist\X` (сборка патчит `0x4a9214` на `FUN_00420f20`; slot 182 биндит
    `rec+0x52c` и ждёт именно полный ключ). Имя без префикса → пустой список →
    fallback;
  - `FUN_0070b020`/`FUN_0070a3a0` вид не трогают — безопасны из EOS-потока;
  - `FUN_004369a0` для ключа-**сущности** (`artist`) из EOS-потока делает
    `trap(7)` (view-ловушка) — сущности читать только через `FUN_0070b020`.
