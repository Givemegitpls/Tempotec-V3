# Переход «альбом → следующий альбом того же автора»

Статус: **сделано и проверено на устройстве (2026-10-09)** для перехода
альбом→альбом. Переход «последний альбом автора → следующий автор» пока НЕ
сделан (в этом случае поведение прежнее — глобальный список).

Скрипт: `tools/exp_shuffle_hierarchy.py` (в цепочке `tools/verify_build.py`
после `exp_shuffle_guard`). Разбор стока — `work/stock_album_step_design.md`.

## Проблема

При включённой настройке «Play through albums» (`album_skip`) после завершения
альбома плеер звал `FUN_004eae80`, который брал следующий/предыдущий альбом из
**глобального** `ALBUM_TABLE` (автор не учитывался) → уводило к чужому автору.

## Причина (разбор стока)

- В стоке клик по альбому в списке артиста (`FUN_004a9360`) давал ключ
  `artist\<Артист>\<Альбом>` → вид `songs_of_an_album_and_an_artist` (kind 8);
  гейт автоперехода `FUN_0042bf40` (префикс `album`) для `artist\…` **ложный** →
  глобального перехода не было.
- Наш патч обложек (`exp_album_view`) увёл клик на `FUN_004a9680`, который всегда
  ставит префикс `album` → ключ `album\<Альбом>`, kind 6 → гейт истинный →
  переход по глобальному списку.

## Решение

Два хука (заглушки в `.text`-пещере `0x4194a0`/`0x419600`, `jal` разрешён):

1. **Контекст автора** — при открытии списка альбомов автора (`FUN_004a9180`,
   хук `0x4a9288`; `s6` = ключ вида) в `.data`-дыре `0xb02bf0` пишется тип
   (`artist`=1 / `album_artist`=2) и ключ вида (`artist\X` / `album_artist\X`).
   Любой другой ключ (верхние «Альбомы») → тип 0.
2. **Подмена альбома на переходе** — хук `FUN_004eae80` (`0x4eaf2c`, вместо
   `jal FUN_004369a0`): если контекст задан и ключ плейлиста `album\<Альбом>` —
   перебираем **штатной** `FUN_004369a0(ключ_автора, i, scratch)` (i=0..63) список
   альбомов автора, ищем запись с `scratch+0x42c` == `rec+0x20c` (текущий альбом),
   берём соседнюю по направлению и копируем её имя в `rec+0x20c`; далее
   `FUN_004eae80` делает всё сам. Иначе/ошибка — штатный `FUN_004369a0` (fallback).

Почему не SQL из хука: подготовка/биндинг запроса из своего кода в потоке
завершения трека не срабатывают. Штатная `FUN_004369a0` работает (её же зовёт
`FUN_004eae80`).

## Грабли

- Wide-слово префикса собирается как `второй_символ<<16 | первый_символ`:
  `artist` = `0x0072_0061` (не `0x0061_0072`), `album_artist` = `al` (`0x006c_0061`).
  Ошибка здесь → тип 0 → fallback (так и было сначала: Artists не работал,
  Album Artist работал, т.к. проверка `al` была верной).
- В kind-9-записи имя альбома лежит и в `rec+0x20c`, и в `rec+0x42c`.

## Проверка на устройстве (пройдена)

Artists → `Дэн Субботин` → альбом → доиграл → следующий альбом `Дэна`;
Album Artist → `Дэн Субботин` → аналогично; «назад» с первого трека → предыдущий
альбом. Следующий автор — пока нет.

## Известное поведение / что осталось (на момент передачи)

**Проверенная сборка:** бинарь `fde1e6c26e08a7909ceeb4b4e1b93ce9` — ровно тот код,
что в `tools/exp_shuffle_hierarchy.py` (образ `out/v3_analog_albumstep.upt`).

- **Последний альбом автора повторяется.** Если текущий альбом — последний в
  списке автора, `FUN_004369a0(ключ, count)` возвращает ту же (последнюю) строку,
  и хук копирует её обратно → альбом играет заново (вместо перехода «по глобальному»
  или «к следующему автору»). **В коде фикса нет** — это известное поведение.
  План фикса: после выбора целевой записи сравнить её имя с текущим (`rec+0x20c`);
  если совпало — уйти в штатный fallback.
- **Переход к следующему автору** (после последнего альбома автора) не сделан.
  Идея: когда целевой индекс выходит за список автора — брать следующего автора
  из `ARTIST_TABLE`/`ALBUM_ARTIST_TABLE` и его первый альбом. Учесть контекст
  раздела (тип 1/2 уже хранится в `0xb02bf0`).
- **Адреса:** `FUN_004369a0` (`0x4369a0`), `FUN_004eae80` (`0x4eae80`),
  `FUN_004a9180` (`0x4a9180`).
